## 三、状态快照

**定位**：断点恢复卡，不是实时仪表盘。15行。

### 📥 注入（AI 读快照）

| 时机 | 动作 |
|------|------|
| 会话开始 | ✅ 必须 |
| `/reset 按快照重来` | ✅ 必须 |
| `/clear` 清空上下文后 | ✅ 必须 |
| 正常对话中 | ❌ 不重复 |

### ✏️ 更新（修改快照文件）

| 时机 | 动作 |
|------|------|
| 跑团中 HP/弹药/时钟波动 | ❌ 只改 JSON，不改快照 |
| 章节完结 · B审计后 | ✅ 全量刷新 |
| 手动说 "存档" | ✅ 全量刷新 |
| 角色卡硬修改（IP升级等） | ✅ 更新受影响字段 |

### 口诀

```
JSON 是唯一事实源，快照是断点恢复卡。
会话起读卡，/reset 重读卡，章末换新卡。
中间跑团不看卡——AI 靠对话不靠卡。
```

## 四、审计体系

### 三级审计

| 类型 | 触发 | 项数 | 作用 |
|------|------|------|------|
| **A 会话启动** | 开局 | 8项（快照 vs JSON） | 防跨会话腐烂 |
| **B 章节完结** | 盖章"已完成" | 18项（11数值+7剧情） | 深度全量校验 |
| **C 变更触发** | 改角色卡 | 3-5项 | 波及范围校验 |

### 审计联动

```
B 审计通过
  ├─ 追加 Octo_审计记录.md
  ├─ 更新 Octo_跑团履历.md
  ├─ 全量刷新 Octo_状态快照.md
  └─ 章节标记 → 已完成

C 审计通过
  ├─ 追加审计记录
  └─ 更新快照中受影响字段
```

### 角色卡修改流程

```
改 JSON → 改 MD → 跑 C 审计 → 通过后更新快照 → 追审计记录
```

审计不通过 → 不更新快照、不标记已完成。

## 七、云端数据架构

### 7.1 四层数据架构

```
L0 · PDF终极真相（不修改，可回溯）
 │  PyPDF2 提取 → 清洗 → 格式化
 ▼
L1 · rules/*.md（可grep的raw dump，不完全可信）
 │  Python正则解析 → 强类型字段校验 → MCP批量插入
 ▼
L2 · 腾讯云 SmartSheet（结构化+已纠错，AI查询目标）
 │  按需生成排版文档
 ▼
L3 · 腾讯云 SmartCanvas（人类阅读排版，参考用）
```

**数据流向**：PDF → MD（提取，人工抽查）→ SmartSheet（解析+校验+人工diff）→ SmartCanvas（按需生成）
**查询优先级**：SmartSheet → MD → PDF（从快到慢，从可靠到原始）

### 7.2 核心原则

1. **角色数据不上云**：JSON/快照/审计记录保留本地，离线安全
2. **不搬规则正文**：只搬速查表和结构化数据
3. **上云即纠错**：SmartSheet强类型字段自动清洗OCR残留（空格/数字失真/表格坍塌）
4. **确定性解析优先**：Python正则解析（零幻觉）→ SmartSheet类型校验（自动拦错）→ 回读diff（人工只看差异）

### 7.4 SmartSheet 字段设计规范

每张表的字段设计原则：
- **price字段用currency类型**：自动校验"100欧元（略贵）"→ 提取数值100
- **boolean用checkbox类型**：如"x2标记"→ checkbox
- **枚举用singleSelect类型**：如"安装设施"→ 购物中心/诊所/医院/芯片插槽
- **数值用number类型**：如"伤害 2d6"→ 拆为"伤害骰数"2 + "伤害面数"6 两个number字段
- **OCR残留自动清洗**：如"赛 博 手臂"→ 正则合并空白

### 7.5 数据提取流水线

```
Step 1: Python正则解析 rules/*.md
  ├─ 确定性提取（零幻觉）
  ├─ 输出结构化JSON（每张表一个文件）
  └─ 标记无法解析的行 → 人工审核清单

Step 2: MCP批量插入 SmartSheet
  ├─ add_table → add_fields（创建表结构）
  ├─ add_records（批量插入，每批≤50行）
  └─ 类型校验自动拦截异常数据

Step 3: MCP回读 + Python字段级diff
  ├─ list_records 回读全量数据
  ├─ 与Step1的JSON逐字段比较
  └─ 只输出差异行 → 人工审核（预计<5%差异）

Step 4: 人工审核通过 → 标记表状态为"已验证"
```

**为什么不用AI直接读MD写入SmartSheet**：AI会幻觉——改字段名、编造不存在的行、遗漏数据。Python正则是确定性的，虽然有解析失败的风险，但失败=报错=不写入，远好于静默幻觉。

### 7.8 AI 查询规则

跑团/建卡中 AI 需要查规则时：
1. **先查 SmartSheet**（L2）：list_records + filter → 结构化数据，最快最可靠
2. **SmartSheet 没有或不够详细** → 读 rules/*.md（L1）：grep 关键词
3. **MD 也不确定** → 回到 PDF（L0）：最终真相源

**禁止**：凭模型记忆回答规则数值。所有数值必须有据可查。

### 7.9 MCP 批量写入规范

> 2026-05-03 由 BCD 批次并行插入事故总结。违反则触发 400007 全局限流。

- **禁止并行写入**：同一空间同时只能有一个写请求（add_records/update_records/delete_records）。
- **单次插入 ≤ 20 行**：超过 20 行的数据必须分批。
- **间隔 ≥ 3 秒**：两次连续写入之间至少延迟 3 秒。
- **重试策略**：遇到 400007 错误时，等待 60 秒后重试一次；仍失败则停止并报告人工干预。
- **优先使用本地脚本**：大批量数据（≥100 行）建议直接调用腾讯云 API 而非 MCP。

## 八、核心铁律

1. 换会话/章节完结 → 跑一次审计
2. JSON 是唯一数据源，MD 是影子
3. 所有消耗当场追踪（弹药/现金/IP/时钟）
4. 只引用本地文件，不凭记忆说"原版是……"
5. 快照是断点恢复卡，不是实时仪表盘
6. 规则正文留本地，速查表上云端
7. 角色数据不上云（JSON/快照/审计 = 离线安全）
8. 上云数据必须经过 Python 正则解析（零幻觉），禁止 AI 直接编造写入
9. SmartSheet 强类型字段是第一道防线，解析失败的行不写入、不跳过
10. MCP 批量写入必须串行、分批、间隔，禁止并行代理密集调用；遇 400007 等 60 秒重试一次，仍失败则停止

## 九、设计历程

> 本次会话（2026-05-03）从 IP 升级规则争议开始，最终建立了完整的防数据腐烂体系。

### 触发点

- 长枪射击 5→6 升级，中文规则书 IP 表是累积还是单次？多轮讨论后确认：累积计算，标准技能每级固定 20 IP
- 过程中发现冲锋枪在角色卡里挂错了技能（长枪→手枪）

### 问题暴露

审计 JSON 角色卡时，连续发现多个数据腐烂：

| 发现 | 严重度 |
|------|--------|
| HP 25 应为 40 | P0 · 建卡时就算错，跨三个会话未发现 |
| 重伤阈值 12 应为 20 | P0 |
| 预算合计差 500 eb | P1 |
| 死亡豁免格式写混了 | P2 |
| stashed 武器标签张冠李戴 | P1 |
| 两版调查档案文件名与内容颠倒 | P2 |
| 升级日志时间标错章节 | P1 |
| 弹药消耗未追踪 | P2 |

### 设计推导

1. **发现 → "需要一个审计流程"** → 设计三级审计（A/B/C）
2. **审计需要数据源 → "JSON 是唯一事实源"** → MD 降为影子副本
3. **文件太多容易忘 → "AI 需要分层读取指令"** → T1/T2/T3 三级
4. **跨会话 AI 会忘 → "开局只读一屏状态"** → 15行精简快照
5. **快照什么时候更新 → "注入≠更新"** → 两动作分离，章末才全量刷新
6. **AI 跑偏怎么办 → "/reset 按快照重来"** → 一键恢复
7. **规则查起来太慢 → "云端速查表"** → 不加规则正文，只加速查询

### 关键取舍

- **快照不中涂更新**：拒绝了"HP 变一点就改快照"的方案，跑团中只改 JSON
- **不写审计脚本**：MD 表格 + 中英混排解析必翻车，AI 手动过清单更可靠
- **不上云角色数据**：JSON 是唯一事实源，离线不可用 = 风险
- **不引用工作区外的数据**：发现自己在凭记忆引用"英文原版公式"后，定了这条铁律
