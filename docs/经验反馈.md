# MCP Server 开发经验反馈

> 从 0 到 1 搭建 Cyberpunk RED MCP Server 的全流程复盘  
> 2026-05-04 — 2026-05-05

---

## 一、项目概述

为 Cyberpunk RED 单人跑团搭建本地 MCP Server，通过 stdio 协议对接 WorkBuddy，提供掷骰、规则速查、随机表三大跑团能力。

**产出：**
- 2 个 Python 文件（server.py 595 行 + loader.py 174 行）
- 486 条结构化规则 + 37 张随机表
- 7 个 MCP 工具（3 跑团可用 + 4 管理待重做）
- WorkBuddy 端到端集成验证通过

---

## 二、做对了什么

### 2.1 数据先行，代码在后

在写任何 MCP 代码之前，把 PDF 规则书转成了 486 条结构化 JSON + 37 张随机表。数据格式统一、元数据完整，启动加载零报错。

**教训：** 如果边写代码边调数据，两边 bug 交织排查成本指数增长。

### 2.2 调研开源，不自造轮子

- 查了 4 个开源 TTRPG MCP Server，全部不适用 → 自建方案有据可依
- 骰子解析选了 `dice` 库（10 年成熟），发现自写的 `scripts/roll.py` 有 `dN-M` 崩溃 bug
- MCP 框架选 FastMCP，比原生 SDK 减少 60% 代码量

**教训：** 10 分钟调研省 10 小时 debug。骰子解析这种"看起来简单"的模块最危险。

### 2.3 极简实现，拒绝过度设计

2 个文件、769 行代码完成 7 个工具。FastMCP 的 `@mcp.tool` 装饰器自动推断 JSON Schema，省掉手写参数定义。数据全量加载到内存（~300KB），零文件 I/O。

**教训：** 教科书上的模块拆分（dice.py / tools.py / server.py / loader.py）在 300KB 数据场景下是噪音。

### 2.4 端到端验证，不信任单元测试

WorkBuddy ToolSearch 确认工具可见 → 逐工具实弹调用 → 人工验证返回值。`roll("2d6+3")` 真的返回 `[2,6]+3=11`，不是模拟测试说的"应该能跑"。

**教训：** MCP 工具的价值不在"注册成功"，在"WorkBuddy 对话里 AI 能调用并拿到正确结果"。

### 2.5 诚实诊断，不修补烂代码

当用户质疑 4 个管理工具是否多余时，直接读 `search_rules` 源码 — 发现查询引擎完全不读扩展数据。承认 toggle 是空壳，不做徒劳修补。

**教训：** 为已有代码辩护是工程师的本能，「这代码不值钱，重来吧」才是正确的反应。

### 2.6 用户主导设计，AI 做分析

Mod 管理器方向的三次关键纠正都来自用户：
- "类似 mod 管理器" — 从数据库思维切换到游戏思维
- "不需要那么复杂" — 砍掉冲突检测和优先级数值
- "基底 + 拓展包 + 房规" — 锁定真实场景

**教训：** AI 擅长枚举方案和分析后果，不擅长判断"什么是真正需要的"。设计决策让用户做。

### 2.7 看准下一步优先级

工具给了 AI 手脚，但 AI 不知道怎么当 GM。下一步不是更多基础设施，而是写 Skill 教 AI 用工具。

**教训：** 功能完备 ≠ 用户体验好。AI 面对 3 个工具不知道先调哪个，需要 Skill 做"大脑"。

## 三、踩过的坑

### 3.1 WorkBuddy MCP 安全机制（耗时最长）

| 尝试 | 做法 | 结果 |
|------|------|------|
| 1 | 写 `~/.workbuddy/.mcp.json` | ❌ WorkBuddy 重启后覆盖 |
| 2 | 写 `mcp-approvals.json`（hash 格式） | ❌ 格式不匹配 |
| 3 | 写 `mcp-approvals.json`（server_name 格式） | ❌ 文件被忽略 |
| 4 | 加 `enableAllProjectMcpServers: true` | ❌ 设置不生效 |
| 5 | **WorkBuddy UI → 设置 → MCP → 信任** | ✅ 用户自行发现 |

**根因：** WorkBuddy 的 MCP 安全层必须在 UI 手动批准，配置文件无法绕过。

**铁律：** MCP 集成不要试图用配置文件绕过安全审批。告诉用户去哪里点"信任"。

### 3.2 扩展管理工具从头空转

`prepare_extension` / `import_extension` / `list_sources` / `set_source_priority` 四个工具写了 200+ 行代码，但 `search_rules` 和 `roll_table` 根本不读它们产出的数据。

**根因：** 从数据模型（三层规则）出发设计工具，而不是从跑团场景（GM 需要什么）出发。

**铁律：** 一个工具在设计阶段就要回答"谁会在什么时候用"。没有使用场景的工具不要写。

### 3.3 Mod 管理器过度设计

第一版 Mod 管理器方案包含：加载顺序、冲突检测、优先级数值、覆盖协议、版本锁定。实际需求：加载 + 合并 + 开关。

**根因：** AI 从教科书的"插件系统设计"出发，而不是从用户的"我就两个包，偶尔关一个"出发。

**铁律：** 先问用户有多少个包、什么场景用，再设计能力。不为不存在的需求做架构。

### 3.4 stdout 污染阻塞 stdio 通信

`loader.py` 中 `print()` 输出日志直接写到了 stdout，干扰 MCP 协议的 stdin/stdout 通道。

**修复：** `print(..., file=sys.stderr)`

**铁律：** stdio MCP Server 的所有日志必须输出到 stderr，stdout 是 MCP 协议的独占通道。

## 四、关键设计决策回顾

| 决策点 | 选项 A | 选项 B | 最终选择 | 理由 |
|--------|--------|--------|---------|------|
| MCP 框架 | 原生 mcp SDK | FastMCP 3.x | **FastMCP** | 装饰器自动推断 Schema，代码量 -60% |
| 骰子引擎 | 自写 dice.py | `dice` 开源库 | **dice 库** | 10 年成熟，覆盖所有语法，零 bug 风险 |
| 通信方式 | HTTP/SSE | stdio | **stdio** | 零配置，自动生命周期，同一台机器无网络延迟 |
| 数据加载 | 懒加载 | 启动全量加载 | **全量加载** | 300KB 总数据量，加载 < 50ms，懒加载无收益 |
| 项目结构 | 4 文件分离 | 2 文件合并 | **2 文件** | FastMCP 吸收 tools.py，dice 库替代 dice.py |
| 规则包管理 | 4 工具 + 配置系统 | Mod 管理器 + toggle_mod | **Mod 管理器**（待实现） | 从游戏思维出发，砍掉不必要复杂度 |

## 五、可迁移铁律

这些原则不限于本项目，适用于任何 MCP 或工具型项目：

1. **数据先定型，代码后启动。** 数据格式不稳定时写逻辑是徒劳。
2. **先用现成的，再想自造的。** pip install 一分钟的事，自写 debug 一天起步。
3. **工具要有使用场景。** 如果一个工具说不清"谁在什么时候用"，砍掉。
4. **端到端验收。** MCP 工具不是"能注册就行"，是在 WorkBuddy 对话里 AI 能拿到正确结果。
5. **发现烂代码时砍掉，不修补。** 200 行空壳代码删掉比重写更快。
6. **用户做设计决策，AI 做分析。** AI 给方案和后果，用户选方向和粒度。
7. **stdout 是协议的，stderr 是你的。** stdio MCP Server 的第一条规则。
8. **不为不存在的场景设计。** "以后可能有 10 个扩展包"不是现在加冲突检测的理由。
