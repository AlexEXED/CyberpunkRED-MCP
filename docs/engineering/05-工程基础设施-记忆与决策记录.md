# 工程基础设施：记忆、决策与质量保障

> 来源：CPRED MCP Server 的跨会话记忆体系、设计决策管理、测试系统
> 适用：任何需要 AI 持续协作且跨会话的项目

---

## 一、问题：AI 每次都失忆

AI 每次会话醒来是空白的。如果每次都要重新解释项目背景，效率会指数级下降。

### 解决方案：三层记忆体系

```
MEMORY.md     ← 长期记忆，项目约定和偏好，常更新
HANDOFF.md    ← 会话交接，当前阻塞和下一步，每会话更新
每日记忆       ← 按日期记录，审计可追溯，30天后压缩进 MEMORY
```

### 各层职责

| 文件 | 内容 | 更新频率 | 消费时机 |
|------|------|---------|---------|
| MEMORY.md | 工作区定位、项目描述、文件索引、研究方法 | 项目约定变化时 | 每次会话开始 |
| HANDOFF.md | 当前目标、已完成、失败尝试、关键决策、当前阻塞、下一步、快速启动命令 | 每会话结束时 | 每次会话开始 |
| YYYY-MM-DD.md | 每日工作记录：做了什么具体操作 | 每次实质性工作后 | 审计/回顾时 |

### HANDOFF.md 格式标准

```markdown
# HANDOFF — 当前状态

> **最后更新：** 日期 时间
> **使用模型：** xxx
> **交接序列：** #X（简短说明）

## 1. 当前目标   # 一句话说清现在在干什么
## 2. 已完成     # 完成清单，打勾
## 3. 失败的尝试 # 知道什么不该做，比知道该做什么更重要
## 4. 关键决策   # 本次会话新增的锁定决策
## 5. 当前阻塞   # 如果有，必须写明
## 6. 下一步     # 优先级排序的待办
## 7. 快速启动命令 # 让下一个 AI 能直接开始干活的命令
## 8. 相关文件   # 按模块分组的文件索引
```

### 关键原则

- HANDOFF 写"为什么"和"下一步"，不是流水账
- "失败的尝试"比"已完成"更有价值——防止重复犯错
- 快速启动命令必须可以直接复制粘贴执行，不写注释

## 二、设计决策管理：PROJECT.md

### 为什么需要架构锚点

多模型协作时，如果没有唯一权威的设计文档，不同 AI 会基于"各自的记忆"做出冲突的设计决策。

### PROJECT.md 结构

```markdown
# PROJECT.md — 项目总纲

## 一、项目定义          # 是什么、不是什么
## 二、数据架构          # 数据怎么组织、怎么分层
## 三、工具集            # 有哪些工具、干什么用
## 四、当前状态          # 已完成/待实施/已知风险
## 五、目录结构          # 物理文件布局
## 六、技术决策          # 所有锁定决策，按版本分组
## 七、铁律              # 不可违反的底线
```

### 决策记录格式

每条决策有编号（D1-D32），按版本分组（v1/v2/v3），包括：
- **决策内容**：锁定的是什么
- **结论**：具体约定
- **日期**：什么时候定的

```
| D23 | 转向声明 | 导入阶段必须大量依赖人力协同 | 2026-05-07 |
```

### 铁律

铁律不是建议，是底线。本项目有 9 条，包括：
- PROJECT.md 是唯一架构锚点
- core 数据永不被覆盖
- archive 只进不出
- MCP 通过 stdio 实际调用验证
- user 层是最终解释权

## 三、测试体系：从一次性到可持续

### 教训

第一次 41 用例烟雾测试由 Claude 跑完顺手删了。测试是永久资产，不是一次性消耗品。

### 解决方案：TEST_CHECKLIST.md

```
# TEST_CHECKLIST

## 测试范围
- roll: 7 用例
- search_rules: 13 用例
- roll_table: 9 用例
- 管理工具: 9 用例（v2 记录保留）
- 端到端: 3 用例

## 执行记录表
| 日期 | 执行者 | 版本 | 结果 |
|------|--------|------|------|
```

### 使用方式

1. 代码变更后，启动 MCP Server
2. AI 通过 stdio 逐项调用工具
3. 勾选清单，记录失败项
4. 更新执行记录表

### 为什么是烟雾测试而非单元测试

MCP 的价值在跨进程通信。单元测试测不出 stdio 集成问题。"通过 stdio 实际调用"是唯一有效的验证方式。

## 四、工作区管理

### 项目拆分原则

当项目出现两种以上不同性质的工作流时，应该拆分工作区：

```
CyberpunkRED-MCP/     ← MCP 工具开发（工程视角）
CyberpunkRED-RPG/     ← RPG 跑团测试（玩家视角）
_shared/              ← 共享规则数据和反馈通道
```

### 共享接口

```
_shared/FEEDBACK.md   ← RPG → MCP 缺陷回流（单向）
_shared/rules/        ← 共享规则数据（双向）
SHARED.path           ← 各工作区定位共享区的路径指针
```

### 什么时候需要 HANDOFF

以下任一条件满足就需要 HANDOFF：
- 项目有 3 个以上文件需要理解上下文
- 使用了多个 AI 模型协作
- 会话之间有超过 24 小时间隔
- 有未完成的阻塞等待另一个会话处理

| MEMORY.md | 长期记忆 | 每次重新解释项目约定 |
