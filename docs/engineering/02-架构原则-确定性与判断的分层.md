# 架构原则：确定性与判断的分层

> 来源：CPRED MCP Server 三层执行模型 + 双 MCP 架构
> 适用范围：任何 AI 需要同时处理"硬规则"和"软判断"的场景

---

## 一、核心命题

AI 同时做两件事会出错：既要遵守规则又要做叙事判断。**把这两件事分到不同层，每层只做一件事。**

## 二、三层执行模型

```
叙事层 — 完全自由
  AI 自由发挥：描述、对话、氛围
  ↓ "这个动作该走哪个结算流程？"
路由层 — AI 判断，选项有限
  从 11 个路由节点中选择（N0 纯叙事 ~ N10 时钟推进）
  ↓ "确定节点后，严格按规则结算"
结算层 — 严格锁死
  MCP 工具：掷骰、查表、算伤害
  不可跳步、不可自创
```

### 关键设计

- **节点锁死，边灵活。** 结算入口是固定的，但 AI 选择走哪个入口是灵活的。
- **每条路由有明确触发条件。** "HP 归零 → 死亡豁免"、"NPC 伤亡过半 → 士气检定"。
- **特殊情况走神谕。** 模糊判定点不是让 AI 自由决定是否掷骰，而是扔给神谕表（d100），由骰子决定命运。

## 三、双 MCP 架构：读与写的物理隔离

### 问题

v2 阶段 7 个工具混在一个 MCP 里：跑团工具（roll/search_rules/roll_table）和写入工具（import/remove/set_priority）同进程。跑团时的 AI 视野里包含"删除规则"能力——这是安全隐患。

### 方案

| | 跑团 MCP | 备团 MCP |
|---|---------|---------|
| 服务对象 | AI GM（日常跑团） | 人类 GM（备团时） |
| 能力 | roll / search_rules / roll_table | 扩展导入、数据源管理、卸载 |
| 权限 | 只读 | 读写 |
| 进程 | 独立进程 | 独立进程 |
| 配置 | CodeBuddy 跑团模式 | CodeBuddy 开发模式 |

**物理隔离的核心逻辑：不同场景挂不同 MCP 实例。** AI GM 的视野里根本不存在写能力。

### 协议层不强制

调研结论：MCP 协议本身没有"只读"约束能力。靠三层防御：
1. `instructions` 字段声明用途
2. docstring 说明工具边界
3. 工具内部校验（如拒绝对 core 的删除操作）

## 四、数据层：三层规则模型的来源追溯

```
user       priority=999  最终解释权，不可禁用
  ↑ 覆盖
third_party  priority=1-998  按需启用/禁用/卸载
  ↑ 覆盖
core       priority=0    始终加载，不可禁用
```

### 三种扩展模式

| 模式 | 效果 | 使用场景 |
|------|------|---------|
| Add | 新增，不与 core 冲突 | 2070 手册的新武器 |
| Replace | 遮蔽 core 记录（不物理删除） | 2070 版修改武器伤害 |
| Extend | 补充属性，两条并存 | 新增武器的穿甲属性 |

### 关键原则

- **物理覆盖是铁律红线。** core 数据文件永不被第三方修改。
- **Replace 是查询时遮蔽，不是文件级覆盖。** 禁用扩展后 core 记录自动恢复。
- **每条规则带来源身份证：** `_source` + `_source_file` + `_category`。

## 五、消费端多样性：特性，不是缺陷

不同 AI 模型对同一个 MCP 的调用策略不同（何时掷骰、查什么规则、如何叙事）。经验验证：

- Grok 3、V4 Flash、Claude 4.6 三种模型都在 MCP 上通过验证
- 调用时机、策略、叙事口吻各不相同
- **但三个模型对 MCP 返回的数值都铁律认同，无人质疑或篡改**

结论：**MCP 工具层的职责在返回确定性结果处停止。** 消费端的差异属于 GM 风格多样性，不在工具层标准化。

## 六、模糊判定点的处理

现实中的模糊场景（如 NPC 搭话该不该掷骰）三个模型表现不一。这是规则 GM 判断权下放后的正常现象，不是产品缺陷。

处理方案不在 MCP 工具层，而在 GM prompt：
- 提供"何时触发检定"的边界条件指南
- 不确定时走神谕（d100 由骰子决定）
- 不同模型 = 不同 GM 风格，视为可选的消费体验
