# 产品化验证：多模型交叉测试方法论

> 来源：CPRED MCP Server 跑团端 — Grok 3 / V4 Flash / Claude 4.6 三模型实战验证
> 核心结论：MCP 工具层 = 成品。消费端多样性 = 特性，非缺陷。

---

## 一、为什么要多模型测试

单一模型通过 ≠ 产品通过。同一个 MCP Server，不同 AI 的调用行为可能完全不同：

- **调用时机**：模型 A 每次社交互动都掷骰，模型 B 只在有明显对抗时掷
- **调用策略**：模型 A 先 `search_rules` 查 DV 再 `roll`，模型 B 凭记忆直接判
- **叙事风格**：模型 A 战术简报风，模型 B 动作片风

如果你只在 Claude 上测试就宣布"系统没问题"，部署到 Grok 上可能发现调用链路全断。

## 二、三模型验证结果

| 验证维度 | Grok 3 | V4 Flash | Claude 4.6 |
|---------|--------|----------|------------|
| 识别 MCP 存在 | ✅ | ✅ | ✅ |
| 主动调用判定工具 | ✅ | ✅ | ✅ |
| 铁律认同返回数值 | ✅ | ✅ | ✅ |
| 模糊判定点处理 | 偏叙事 | 偏检定 | 中间态 |
| 调用节奏 | 较慢 | 最快 | 中等 |
| 叙事口吻 | 直接 | 流畅 | 详细 |

### 通过的验证项

- **跨模型 MCP 协议兼容**：三个模型都能正确发起 stdio 调用
- **工具返回值解析**：三个模型都能正确读取 JSON 返回
- **数值铁律认同**：无模型质疑或篡改 MCP 返回的骰值和规则文本
- **7 个工具均可达**：每个模型都至少调用了 roll / search_rules / roll_table

### 分歧验证项（非问题）

- 模糊判定点（NPC 搭话、环境探索等）
- 调用时机和策略差异
- 叙事手法的不同风格

**这三个分歧是 GM 消费端的多样性，不是 MCP 工具层的缺陷。** 视为特性而非 bug。

## 三、多模型测试方法论

### 3.1 测试矩阵

```
             roll   search_rules   roll_table   模糊判定   叙事一致性
Grok 3        ✅        ✅            ✅           ↓          ↓
V4 Flash      ✅        ✅            ✅           ↓          ↓
Claude 4.6   ✅        ✅            ✅           ↓          ↓
                                           ↑          ↑
                                      特性差异    特性差异
```

### 3.2 测试流程

1. **相同输入，不同模型** — 跑相同的跑团场景（如"进入酒吧"）
2. **观察工具调用序列** — 记录每个模型的 MCP 工具调用时序
3. **对比调用差异** — 哪些差异是"合理不同"，哪些是"功能缺失"
4. **确认数值一致性** — MCP 返回的数值是否被所有模型正确使用

### 3.3 判定标准

| 发现 | 判定 | 处理 |
|------|------|------|
| 某模型完全不调用某个工具 | 产品缺陷 | 检查工具描述是否清晰 |
| 某模型对返回值的解读错误 | 产品缺陷 | 检查返回格式 |
| 某模型调用时机不同 | 特性差异 | 文档记录，不修 |
| 某模型叙事风格不同 | 特性差异 | 文档记录，不修 |

## 四、产品化完成的判断标准

- [x] 工具层在多个模型上正常运行
- [x] 返回值被所有模型正确解析
- [x] 模型间的差异发生在消费端（GM 判断），不在工具层
- [x] 有测试清单，可在任意模型上复现验证
- [ ] 有真实用户（非开发者）跑通完整跑团流程

本项目的跑团 MCP 已完成前四项，最后一项为持续验证。

## 五、这个方法论的推广价值

任何 AI 工具（不限于 MCP）如果声称"生产可用"，至少应该：

1. 在两个以上不同厂商的模型上验证
2. 区分"工具层问题"和"消费端差异"
3. 不要试图消除消费端差异——那是 AI 的多样性，是你的产品的兼容性证明
