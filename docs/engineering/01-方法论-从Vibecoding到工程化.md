# 从 Vibecoding 到工程化：方法论演进实录

> 来源：CPRED MCP Server（2026-05-04 ~ 2026-05-10）
> 核心洞察：对 AI 的"不信任"是工程化的起点

---

## 一、起点：你以为你在 vibecoding

"帮我写个掷骰工具"——这是项目的第一个 prompt。

一个人、一个 AI、一个想法。快速迭代，想到什么写什么。标准的 vibecoding 开局。

## 二、转折：信任开始瓦解

第一周就出了问题。AI 返回的 JSON 在标准输出外包裹了自然语言解释；字段名 `apiManagerInstance` 和 `APIManagerInstance` 混用；占位数据"看起来能跑"但实际是断裂的。

这些不是 bug，是信号——**AI 输出不可靠是常态，不是异常。**

## 三、工程化方法论的形成

### 3.1 讨论四步法

任何设计决策走同一个流程：

1. **识别** — 问题到底是什么？不只描述症状
2. **分场景** — 把问题拆成多个场景，逐一分析
3. **模拟** — 在脑中跑一遍各场景下系统行为
4. **定案** — 锁定决策，写入 PROJECT.md

不走这四步的讨论会无限循环。走了就能收敛。

### 3.2 四原则

- 不改精神 — 不动规则体系的设计哲学
- 不改数值 — 原始数据原样保留
- 只补空白 — 只在核心规则不覆盖的地方扩展
- 讨论定案 — 任何变更需明确确认

### 3.3 三个架构阶段 = 三个被推翻的假设

| 版本 | 假设 | 被什么推翻 |
|------|------|-----------|
| v1 | core 486 条够用 | 现实需要扩展层 |
| v2 | 一键自动导入 | 鲨鱼包 136 文件打脸：需要人力协同 |
| v3.1 | 单 MCP 够用 | 跑团读和备团写混在一起是安全问题 |

**每一次推翻都来自真实样本，不是理论讨论。** 这是工程化的核心特征——不是设计得完美，而是被现实纠正后留下了可追溯的记录。

## 四、从"信任 AI"到"系统性格挡"

| 阶段 | 心态 | 行为 |
|------|------|------|
| Vibecoding | AI 能做对 | 一个 prompt 搞定，不验证 |
| 原型期 | AI 可能会错 | 手工验证几次 |
| 工程化 | AI 必然在特定位置出错 | 建立系统性防御 |

防御体系详见 [03-AI协作铁律](./03-AI协作铁律.md)。

## 五、判断你是否已脱离 vibecoding

- [ ] 你有版本号，且知道每个版本的区别
- [ ] 你有架构锚点文档（别人能看懂整体设计）
- [ ] 你的设计决策可追溯到具体事件
- [ ] 你有测试清单（不是"上次都验证过了"）
- [ ] 你能说出"这个项目在哪些地方 AI 会出问题"
- [ ] 你的系统能换 AI 模型而不崩
- [ ] 你的代码被另一个 AI 审查过

以上全部打勾，你不在 vibecoding。你在做 methodical AI-assisted engineering。

## 六、关键教训

1. **真实样本是最好的老师。** 理论讨论可以吵三天，鲨鱼包扔进来五分钟就见分晓。
2. **设计文档比代码长寿。** v2 代码被重构了，但 v2 的决策记录仍然锁定在 PROJECT.md 里。
3. **测试资产不可丢弃。** 第一次 41 用例由 Claude 跑完顺手删了，现在固化在 TEST_CHECKLIST.md。
4. **不信任 AI 不是缺点，是工程素养。** 知道它在哪里必然出错并建立格挡——这是你能在三个模型上跑通同一个系统的原因。
