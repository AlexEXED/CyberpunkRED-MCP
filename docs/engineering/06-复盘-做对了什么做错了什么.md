# 做对了什么，做错了什么

> 来源：CPRED MCP Server 完整开发周期（2026-05-04 ~ 2026-05-10）
> 一份诚实的事后评估。供下一个项目参考。

---

## 一、做对了什么

### 1. 第一天就建了 PROJECT.md

不是"等稳定了再写文档"——PROJECT.md 是第一天的产物。32 项决策全部锁定、9 条铁律不可动摇。这个文件阻止了无数次"我觉得可以这样改"的随意迭代。

**教训：架构锚点不是副产品，是第一个产品。**

### 2. 讨论四步法

识别→分场景→模拟→定案。没有这个流程，设计讨论会无限循环。走了这个方法后，每次讨论都有一个终点。

**教训：AI 协作的设计讨论如果没有硬收敛机制，会在无限可能性中漂浮。**

### 3. 拿真实样本打脸自己

鲨鱼包 136 个文件扔进来那刻，v2 的"一键自动导入"假设五分钟内就崩了。这不是失败——这是**最高效的学习方式**。如果继续在理论上讨论"扩展包该长什么样"，可能再吵三天都没结论。

**教训：理论讨论三天，不如数据文件五分钟。**

### 4. 不信任 AI 的态度

这不是消极——这是工程素养。AI 返回的 JSON 不可靠 → 用 MCP 框架序列化。AI 的方案过度设计 → 学会说"太多了，砍掉"。AI 的测试会丢 → 固化为文档。

**教训：知道 AI 在哪里必然出错并建立系统性格挡，是你能在多模型上跑通同一个系统的根本原因。**

### 5. 三模型交叉验证后才说"成品"

Claude 上通过 ≠ 产品通过。在 Grok 3 和 V4 Flash 上也跑了一遍，确认了三件事：工具层稳定、返回值被正确解析、分歧都在消费端。这才敢说"跑团 MCP 是成品"。

**教训：单模型测试 = 未测试。**

### 6. 消费端多样性判定为特性

三个模型的调用时机、策略、叙事风格各不相同。没有去"修"它——判定这是 GM 风格多样性，不是产品缺陷。这个决定避免了无限调优的死循环。

**教训：划定产品边界比实现功能更难。知道什么不该做 > 知道什么该做。**

### 7. 跑团端适时停止

多模型验证通过、边界清晰、功能完整。没有继续往上堆"判定辅助"、"路由建议"之类的过度设计。跑团端到此为止，下一个产品是备团 MCP。

**教训：知道什么时候停，是工程决策中最难的一种。**

### 8. HANDOFF.md 的设计

跨会话上下文交接不是简单的"记录"。它有结构：当前目标、已完成、失败尝试、关键决策、当前阻塞、下一步、快速启动命令。这个结构让下一个 AI 能在 30 秒内接管。

**教训：交接文档的价值不在"写了什么"，而在"下一个 AI 能不能直接开干"。**

### 9. 拒绝碎片化脚本

14 个 Python 脚本听起来多，但它们都是数据构建管道的一部分——PDF 提取、规则结构化、表索引生成。没有为每个小需求写独立脚本，坚持了"一体化工具 > 碎片化脚本"的原则。

**教训：脚本数量不是问题，脚本之间有依赖关系没有文档才是问题。**

### 10. 工作区拆分

MCP 开发一个工作区、RPG 跑团一个工作区、共享规则独立。物理隔离了代码开发和跑团测试的上下文，避免了"改代码时看着角色卡"的混杂。

**教训：当项目出现两种不同性质的工作流时，不拆工作区的代价是上下文污染。**

## 二、做错了什么

### 1. 起点是纯 vibecoding

第一个 prompt 是"帮我写个掷骰工具"。没有设计、没有文档、没有测试。前期的效率是真实的，但后期的债务也是真实的——很多基础决策是在混乱中做出的，后来才被 PROJECT.md 追认。

**改进：下一个项目从 PROJECT.md 开始，不是从第一个 prompt 开始。**

### 2. "一键自动导入"的假设

v2 设计了 prepare_extension → AI Skill → import_extension 的流水线，假设第三方扩展是结构化的单 JSON 文件。现实：鲨鱼包是 136 个混合格式文件（docx、xlsx、jpg），包含机制重写、NPC 卡、范例文本、世界观描述。

**改进：先拿到真实样本再设计导入流程，不要对着想象中的完美数据做架构。**

### 3. 管理工具建了但零调用

prepare_extension、import_extension、list_sources、set_source_priority、remove_extension——五个工具全部实现，但在备团 MCP 完成前，一次都没真正用过。这些代码后来被归档到 _legacy_admin_functions.py。

**改进：不为了"完整性"建超前工具。等真实需求出现再建。**

### 4. 规则模型的反复调整

四层（core/solo/third_party/user）→ 回到三层（core/third_party/user，solo 融入扩展）。solo 层的定位在设计和实施之间来回横跳，消耗了讨论时间。

**改进：数据模型设计应该基于"实际有什么数据"，不是"可能有什么数据"。solo 如果还没有结构化就绪的数据，不要在架构里给它占位。**

### 5. 测试文件跑完就删了

第一次 41 用例烟雾测试由 Claude 执行完毕，测试过程没有被持久化。后来才补建 TEST_CHECKLIST.md。

**改进：测试是永久资产。任何跑完的测试，用例、输入、预期结果必须保留。**

### 6. README 滞后严重

PROJECT.md 已经 v3.1 了，README 还是 v1 的内容。直到今天（5 月 10 日）才重写。新 AI 进来看 README 会产生错误的第一印象。

**改进：架构锚点变更后，README 同步更新。不能只更新内部文档。**

### 7. 对 AI 协作模型的依赖不够自觉

前期的多模型协作是"感觉到需要"而不是"明确设计"：Claude 做代码实现、DeepSeek 做规则研究、Claude 又回头做测试。但 HANDOFF 格式没有区分"不同模型之间的交接"和"同一模型跨会话的交接"。

**改进：如果是多模型协作项目，HANDOFF 应该明确标注"上次用的哪个模型"和"换模型需要注意什么"。**

### 8. 没有在 v1 阶段就建 source_config.json

486 条规则全部灌入内存，没有考虑分层。等到 v2 才引入三层模型。如果 v1 就按 source → 规则的映射来组织数据，v2 的重构成本会更低。

**改进：即使一开始只有一层数据，也用分层思维组织。"只有一个源"不是"不需要源配置"的理由。**

---

## 三、如果可以重来

1. 用 PROJECT.md 开始，不是用 prompt 开始
2. 先拿真实样本，后设计导入流程
3. 从第一天就用分层数据模型（即使只有一个源）
4. 第一个工具上线后立刻写测试清单，不等到 v2
5. README 和 PROJECT.md 同步维护
6. 不建超前工具，等真实需求
7. 跨模型协作时，在 HANDOFF 里标注模型切换注意点

---

## 四、一条最有价值的错误

> **"一键自动导入"的假设。**

不是因为损失最大——它迫使了双 MCP 架构的诞生，长期来看是正确的。而是因为**这条错误来自一个更底层的思维惯性：把"AI 能做的事"等同于"AI 能做好的事"。**

AI 确实能解析 PDF、提取 JSON、判断分类——但你信任它做这些事，而你的用户信任你。当 AI 的分类出错、覆盖了不该覆盖的规则、漏掉了不该漏掉的内容时，买单的是用户的跑团体验。

**人力协同不是"AI 不够强"的妥协，是对"谁能对最终结果负责"的清醒认知。**
