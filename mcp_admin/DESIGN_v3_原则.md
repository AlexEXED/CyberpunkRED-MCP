# MCP Server 扩展系统 v3 — 设计原则

> **日期**: 2026-05-07 | **状态**: ✅ 已敲定
> **范围**: 仅原则。具体设计（manifest 格式、CLI 接口、目录结构等）另行讨论。

> **适用范围**：本文档主要约束**备团 MCP**（数据导入工作流）的设计。
> 跑团 MCP（`mcp_server/server.py`，工具：roll / search_rules / roll_table）维持精简，
> 仅以"只读"方式消费已落地的数据，不受本文档约束。
> 项目采用**双 MCP 架构**：跑团端独立、备团端独立、共享底层数据与业务模块。

---

## 一、转向声明

**v1/v2 隐含假设**：用户给一个 JSON，工具自动验证 + 落地。导入是一次性、机械的、可批量的操作。

**v3 承认的现实**：
真实的第三方扩展（鲨鱼包级别）从原始 docx/xlsx/pdf 到结构化 JSON 的转换，**没有任何自动化路径可以胜任**。它必须依赖：
1. AI 解析能力（用 IDE 内置 docx/xlsx/pdf skill 读原文）
2. 人类决策（字段映射、分类归属、机制裁决）
3. 反复对话迭代（提取一版 → 审核 → 修正）
4. 多次会话累积（一次会话搞不完一个完整扩展包）

**结论**：**导入阶段必须大量依赖人力协同。** 这条作为后续所有 v3 设计的不可触碰地基。

---

## 二、设计原则（十条）

### 原则 1：人力优先，自动化兜底

不追求"一键导入"。工具只做能 100% 机械化的部分（验证、写盘、加载）。所有需要判断的环节，让人/AI 在对话里完成。

### 原则 2：人机分工清晰

| 环节 | 谁做 |
|------|------|
| 读原始文档 | AI（IDE 内置 docx/xlsx/pdf skill） |
| 字段语义理解 | AI + 人 |
| 分类归属决策 | 人（AI 给建议，人拍板） |
| 写出 JSON 草稿 | AI |
| 草稿审核 | 人（关键步骤） |
| 验证字段合规性 | CLI 工具 |
| 写入扩展包目录 | CLI 工具 |
| 加载到内存 | loader.py |
| 在跑团中查询 | search_rules（MCP 工具） |

### 原则 3：先全量转化，再总览分类

导入大型扩展包必须分两阶段，**禁止边读边写**：

**阶段 A — 预处理**：
- 把扩展包内所有原始文档（docx/xlsx/pdf）批量转换为 AI 友好的中间格式（markdown / 结构化文本 / 表格 JSON）
- 保留全部原始信息，**不做任何分类、筛选、删减**
- 产出沉淀在扩展包的中间产物目录中

**阶段 B — 总览分类写入**：
- 基于阶段 A 的全量中间产物，以**总览视角**进行分类筛选
- 按目标分类（equipment / mechanics / npcs / ...）拆分写入正式数据文件
- 此阶段才做合规性裁决、字段映射、Replace/Extend 声明

**为什么必须分两阶段**：
- 边读边写容易因局部视角误判分类归属（例如把"穿甲机制"误塞进 equipment 而非 mechanics）
- 全量预处理后才能识别跨章节关联（同一概念在多个 sheet 出现时如何统一）
- 中间产物可被 AI 反复检索查阅，不必每次重读原文
- 阶段 A 失败可重做，阶段 B 失败也不污染原始资料

### 原则 4：增量与可中断

扩展包的提取过程必须支持：
- 中断后续做（不必一次提完，多次会话累积）
- 局部更新（修正某个章节后重新落地，不影响其他）
- 进度可见（manifest 里记录每个数据文件的状态：pending / in_progress / complete）

### 原则 5：所有原始资料保留在包内

每个扩展包目录必须保留原始 docx/xlsx/pdf 文件。理由：
- 重新提取（修了 bug 后重做）
- 人工查阅（AI 解析有歧义时回原文）
- 版本对比（V1.71 vs V1.70 对照）
- 出团后玩家追溯规则来源

不在意磁盘成本，价值远高于成本。

### 原则 6：失败优于错误

宁可拒绝（让人来处理），不要勉强（产生错误数据）：
- 字段不合规 → 整体拒绝
- 分类不在允许列表 → 拒绝
- 依赖缺失 → 拒绝加载
- Replace 目标找不到 → 警告但允许（不报死，但记日志，让人发现）

### 原则 7：工具自介绍（AI 可发现性）

工具集的价值不仅在"存在"，更在"AI 在备团场景下能主动识别并使用"。必须做到：

- **入口文档显眼**：工作区必须有一份 AI 启动时能立即读到的导入指南（如 `mcp_server/导入指南.md` 或 `scripts/admin/README.md`），说明"有哪些工具、分别做什么、典型流程"
- **CLI 自描述**：每个脚本的 `--help` 必须人话化、结构清晰，AI 能直接复述给 GM
- **字段命名 AI 友好**：manifest、JSON Schema 等字段名避免工程师密语，AI 一看就懂
- **扩展包自带 README**：每个扩展包目录内要有说明文件，记录当前状态、已完成章节、下一步建议
- **进度可读**：manifest 里的 `extraction_progress` 等字段结构化可读，AI 能直接解析并汇报

**验证指标**：AI 首次进入工作区且无任何额外提示时，能向 GM 清晰说出"你现在有哪些扩展、处于什么状态、接下来能做什么"。

### 原则 8：导入工作流由 AI 主导

GM 不负责规划导入步骤，AI 负责。典型工作流：

| 阶段 | GM | AI |
|------|----|----|
| 启动 | "我想导入鲨鱼包" | 主动询问关键决策（包名、依赖、版本号） |
| 创建 | 确认参数 | 调用 CLI 创建包目录 + 拷贝原始资料 |
| 预处理（阶段 A） | 等待 / 审核 | 批量转换 docx/xlsx/pdf 为中间产物 |
| 分类（阶段 B） | **关键裁决** | 读中间产物 → 建议分类 → 写草稿 → 请 GM 审核 |
| 落地 | 确认 | 调用 CLI 验证 + 写盘 |
| 汇报 | 查看结果 | 汇报进度、建议下一步 |

**规则**：
- AI 在每个检查点**向 GM 汇报、等待确认**
- GM 中途离开，AI 能续接（读 manifest 找到上次停在哪儿）
- 关键决策（分类、Replace/Extend、机制裁决）必须由 GM 拍板
- 机械工作（拷贝、格式转换、校验、写盘）由 AI 和 CLI 直接完成，不需要 GM 重复确认

**工具是 AI 的手脚，AI 是 GM 的导游。**

### 原则 9：跨模型一致性 — 工作流外化

工作流的所有约束、状态、流程顺序必须**显式编码到工具与文档中**，不依赖任何特定 AI 模型的内部推理。**任何模型按字面照做都能产出相同结果**。

#### 9.1 约束硬编码
分类、模式、字段格式等硬性约束在 CLI 工具内部强制（拒绝非法输入）。不依赖 AI"知道"规则；AI 不知道也跑不通错误的路径。

#### 9.2 流程显式化
两阶段流程通过 CLI 命令分离（如 `preprocess` 与 `commit` 两个不同命令），AI 跳过阶段会失败。manifest 记录当前阶段，下一阶段命令会检查前置阶段是否完成。

#### 9.3 状态外置
进度、决策记录、待办事项都写在 manifest / 状态文件里。AI 不需要"记住"上一步做了什么，读文件就行。所有工具操作都向状态文件写入，不依赖会话上下文。

#### 9.4 导航外置
"下一步该做什么"由专用 CLI 输出（如 `pack_status` 给出建议）。AI 不自己推断，调用工具问。

#### 9.5 入口唯一
整个导入工作流有一个**唯一入口文档**，所有 AI 模型从这里开始。入口文档明确指向所有其他资料和工具，其位置在 PROJECT.md / README.md 中显眼标记。

#### 9.6 契约明文
所有 CLI 输出 JSON 化（或结构化文本），不同模型解析结果一致。错误码、状态字段都是预定义集合，不是自然语言描述。

**验证指标**：把同一份"导入某扩展某章节"任务交给不同 AI 模型独立运行，产物的目录结构、字段命名、状态机流转必须完全一致。

### 原则 10：抗污染 — 工作流自防御

工作流必须在 AI 处于劣势状态（上下文过长、注意力衰减、任务混杂、能力较弱模型）时**仍能产出合格结果**。设计目标：**让走错路径变得困难，让走正确路径变得便宜**。

#### 10.1 单轮重启可用
任何 AI 即使**清空所有上下文**，仅凭工作区内的入口文档 + 当前 manifest 状态，也能继续推进工作。不依赖"上一轮我们说过"，不依赖"我记得"，一切关键决策、约定、状态都在文件里。

**实测方法**：删掉 AI 历史，让它从零开始读工作区，能不能接着干？能 = 通过。

#### 10.2 原子化任务
每次 AI 执行的任务粒度要小，单次操作不超过几个 CLI 命令。manifest 的最小执行单元应是"章节级"或"sheet 级"，不是"包级"。

#### 10.3 操作前强制核对状态
AI 在执行任何写入操作前，**必须先调用状态查询**，不允许凭"印象"操作。写入类 CLI 在执行前先校验 manifest 状态，状态不一致则拒绝写入并给出引导。AI 不能跳过校验。

#### 10.4 弱模型友好
针对中端模型设计，不为强模型优化：
- CLI 帮助文本短、结构化、有典型示例
- 错误信息明确告诉 AI"下一步该做什么"，不要只报"什么错了"
- 字段名简短不歧义
- manifest 字段不超过 1 层嵌套

#### 10.5 脏上下文兜底
设计假设 AI 当前会话已累积了大量与导入无关的内容。
- 工作流相关 CLI 输出格式与跑团 CLI **完全不同**（视觉上一眼能识别）
- 入口文档用强提示语：「**导入工作流开始**：以下指令必须严格执行」
- AI 在切入导入流程前，应被引导显式重置心智（先调用状态查询看现状，再决策）

#### 10.6 失败可恢复（幂等）
任何中间产物的写入都是幂等的：同一份草稿重复 commit 不会报错也不会重复写入；中断后再来一次能恢复；错误的写入能通过 CLI 撤销，不留垃圾。**让 AI 敢于尝试，因为试错成本低**。

**验证指标**：把"继续导入某扩展"任务交给一个累计了 50k token 杂项对话的会话，不允许提示模型"先看 manifest"。AI 应主动读入口文档或调用状态查询、正确说出当前进度、提议的下一步与 manifest 一致、执行的命令格式与之前会话产出一致。

## 三、对工具集的影响

### 3.1 MCP 工具集瘦身

跑团 AI 不应触碰扩展管理。MCP Server 仅暴露跑团工具：

| 工具 | 角色 |
|------|------|
| `roll` | 跑团消费 |
| `search_rules` | 跑团消费（v2 分层逻辑保留） |
| `roll_table` | 跑团消费 |

管理工具（`prepare_extension` / `import_extension` / `list_sources` / `set_source_priority` / `remove_extension`）从 MCP Server 移除。

### 3.2 管理能力下沉为命令行工具

由 GM/用户在终端运行的 CLI 工具承担管理职责。CLI 不是"自动化工具"，是**人力协同的检查点**：

| CLI 不应做 | CLI 应做 |
|----------|---------|
| 自动从 PDF 提取数据 | 接收人/AI 整理好的 JSON 草稿 |
| 自动判断字段映射 | 验证字段是否合规 |
| 自动决定分类归属 | 检查 `_category` 是否在允许列表 |
| 自动解决 Replace 冲突 | 报告冲突，让人决定 |

**CLI 的角色是"门卫"，不是"工人"。**

### 3.3 接受导入成本

扩展包不是"产品"，是"工程"。一个鲨鱼包级别的扩展，预计需要数十次会话累积才能完整导入。**这是设计选择，不是缺陷**。
